# Farmily: Why a Document Model Suits the Case Study

This document explains how Farmily was modelled in MongoDB (`farmily-mongo.js`), why a document model suits parts of the case study, and what it costs compared with the PostgreSQL design from Portfolios 1 to 3. The screenshots `mongo1` to `mongo5` are the evidence.

## 1. The model

The database has five collections (`mongo1-database-built.png`: 5 farmers, 4 customers, 12 listings, 6 orders, 8 reviews). The key design question in a document database is, for each relationship, whether to **embed** the related data inside the document or **reference** it by ID in another collection. The rule I followed: embed what is read together and stays small; reference what grows without limit.

| Collection | What it holds | Embedded | Referenced |
|---|---|---|---|
| `farmers` | Profile, plus a stored rating summary (`review_count`, `avg_rating`) | Rating summary | Reviews (by `farmer_id`) |
| `customers` | Profile and addresses | Addresses | Orders (by `customer_id`) |
| `listings` | One harvested batch: product, category, price, stock, and an `attributes` object that differs by product | A copy of the farmer's ID, name and region | The full farmer profile (by `farmer_id`) |
| `orders` | A whole order | Order items, payments, deliveries, a copy of the delivery address, and the customer's ID and name | Listings and farmers (by `listing_id` and `farmer_id` inside each item) |
| `reviews` | One review each | Nothing | Customer, farmer and listing (by ID) |

**Embedded.** Order items, payments and deliveries are always read with their order, and each list stays short: an order has a few lines, at most a couple of payment attempts (order 50010 has a failed card payment followed by a bank transfer) and one delivery per farmer. A customer's addresses are also few and are only used with that customer. Embedding them means one read returns everything, and that one document can be changed atomically. Each order item also stores `unit_price` as a copy of the price at purchase time, which plays the same role as `unit_price_at_purchase` in PostgreSQL.

**Referenced.** Reviews are the one relationship that grows without limit: a popular farmer could collect thousands. MongoDB limits a single document to **16 MB**, so embedding every review in the farmer document would eventually fail, and every read of a farmer's profile would load all of them. Reviews are therefore kept in their own collection, linked by `farmer_id`, with an index on that field. To avoid averaging thousands of reviews whenever farmers are ranked, the farmer document stores a small summary (`review_count`, `avg_rating`), which is updated each time a review is added (`mongo4a-ratings.png`).

## 2. Why it suits Farmily

**Flexible attributes that differ by product** (`mongo2-attribute-search.png`). Each kind of produce is described by different facts: tomatoes have a ripeness, a crate weight and whether they were cold-stored, rice has a moisture percentage, bag sizes and whether it was destoned, and plantain has fingers per bunch. In MongoDB these simply sit in each listing's `attributes` object and can be searched directly. Q2a found firm tomatoes in crates of 20 kg or more (listing 40, Halima Garba Farms, 25 kg crates), and Q2b found destoned rice with moisture below 12.5% (listing 22, 11.8%). Adding a new product with new attributes needs no schema change. In PostgreSQL the same data would need either many nullable columns on `produce_listings` (`ripeness`, `crate_weight_kg`, `moisture_pct` and so on, most of them empty for any given row), or a separate attribute table with one row per attribute (entity–attribute–value), which needs a join for every search condition and loses type checking because every value is stored as text.

**An order is read as one document** (`mongo3-orders-and-sales.png`). Q3 returned customer 42's three orders with their number of lines and their totals (for example order 50002: 2 lines, 85,865.80) from the `orders` collection alone. In PostgreSQL the same result needs `orders` joined to `order_items` and grouped, and the payments and deliveries would each need another join. The total is still calculated from the embedded items rather than stored, as in Portfolio 1.

**A buyer's search needs no join** (`mongo1-database-built.png`). Each listing carries a copy of its farmer's name and region, so Q1 returned the active Ofada rice listings, cheapest first, with the farmer's details, from one collection. The equivalent PostgreSQL query (Portfolio 2, Q1) joins `produce_listings` to `farmers`. Search is Farmily's most frequent operation, so it benefits most from this. `mongo5-validation-and-explain.png` also shows that Q1 uses its compound index: `FETCH <- IXSCAN`, examining only the 2 documents it returns, against 12 with a forced full collection scan.

## 3. Trade-offs compared with the PostgreSQL design

**Duplicated data.** The farmer's name and region are copied into every listing, and the customer's name into every order. This is exactly the update anomaly that normalisation removed in Portfolio 1: if Musa Bello Farms changes its name, every one of its listings must be updated as well as the farmer document, and any copy that is missed shows the old name. The copies are worth it only because a farmer's name changes rarely while listings are read constantly. The stored rating summary is a similar choice. Portfolio 1 deliberately did not store `average_rating`; here it is stored, so it must be kept in step with the reviews. `mongo4a-ratings.png` checks the summary against the reviews collection after a new 2-star review: both give 3 reviews with an average of 3.

**Weaker built-in rules.** MongoDB does support schema validation, and it was used: `mongo5-validation-and-explain.png` shows a listing with negative stock and an order with no items both rejected with "Document failed validation". But there are no foreign keys. Nothing stops an order item from pointing to a `listing_id` that does not exist, or a review from naming a farmer that was deleted, and nothing can express the composite rules from Portfolio 1 (an order's address must belong to its customer). Those checks move into the application.

**Atomicity across documents.** An update to one document is always atomic, which covers everything embedded in it: an order and its items, payments and deliveries change together or not at all. Placing an order, however, also reduces the listing's stock, and that is a second document. For the stock itself, a conditional update works as in Portfolio 3 (Fix B): `mongo4b-stock-update.png` shows Buyer A's update (`quantity_available >= 50`, then subtract 50) matching and modifying 1 document, and Buyer B's identical update matching 0, leaving the stock at 0 rather than −50. The demo ran the two updates one after the other in one script, but the protection does not depend on that: because the check and the change are a single operation on one document, a second buyer arriving at the same moment cannot slip between them. What it cannot do is make the order insert and the stock update succeed or fail together; adding a review and updating the farmer's summary has the same gap. MongoDB's multi-document transactions solve this, but they need a replica set, not the single standalone server used here. A replica set is set up in Portfolio 5.

## 4. Verdict

A document model suits part of Farmily, not all of it, so I would use both databases, each where it is strongest. **PostgreSQL** should remain the system of record for orders, payments and stock, where strong consistency matters most: multi-row ACID transactions, foreign keys and the isolation levels from Portfolio 3 protect money and stock without relying on the application. **MongoDB** suits the product catalogue and search, where flexibility and read speed matter most: listings with product-specific attributes, searched constantly and read without joins. In practice, listings would be written to PostgreSQL first and copied to MongoDB for searching. The catalogue could then be a few seconds behind, which is acceptable for browsing, because checkout always confirms the price and stock against PostgreSQL.
